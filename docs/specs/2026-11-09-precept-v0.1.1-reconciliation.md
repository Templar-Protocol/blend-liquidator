# precept-liquidator on Precept v0.1.1

**Date:** 2026-11-09
**Status:** design approved; amends
[2026-09-20 ADR-0008 fork semantics](2026-09-20-adr-0008-fork-semantics.md)
wherever the two disagree. Everything that document says and this one does
not contradict still stands.

## Source of truth

The bot was reconciled with the fork at its pre-release head `54afdae`.
Precept has since released `v0.1.0` (Guardian-audited) and `v0.1.1`, and
every active mainnet market runs `v0.1.1` wasm. This document closes the
three ways `v0.1.1` differs from `54afdae` that the bot does not yet handle.

| Tree | Ref |
|---|---|
| Precept | `Templar-Protocol/precept` tag `v0.1.1`, commit `19cb928` |
| Previous basis | the same repository at `54afdae` (then named `blend-contracts-v2`) |

Line references below are Precept's at `v0.1.1` unless they name a file in
this repository. Error codes, request types, entry-point signatures and
every formula and rounding direction this crate ports are unchanged between
the two; only what is listed here moved.

## 1. What changed

### 1.1 Two event topic layouts

`defaulted_debt` and `debt_setoff` now carry the defaulted user in topic 1
(the borrower, or the backstop on `check_and_handle_backstop_bad_debt`'s
path, which the tracker's re-read then finds with no liabilities) and the
asset in topic 2 (`pool/src/events.rs:179-197`):

- `["defaulted_debt", user, asset]`, data `d_tokens_burnt: i128`;
- `["debt_setoff", user, asset]`, data `(b_tokens_burned, d_tokens_repaid)`.

At `54afdae` both were `[name, asset]`, and stock `defaulted_debt` still is.
`src/chain/xdr/events.rs` requires exactly two topics for both, so on every
live market each such event fails to decode and the poller skips it with a
warning. Every other event's topics and data are unchanged.

### 1.2 A per-reserve `min_position`

`ReserveConfig` gains `min_position: i128`, between `supply_cap` and
`enabled` (`pool/src/storage.rs:71`), at least zero (`pool/src/pool/config.rs:205`)
and, like every reserve field, frozen once the pool leaves Setup. After every
`SupplyCollateral` (`pool/src/pool/actions.rs:450`) and `WithdrawCollateral`
(`:478`), `require_min_position` (`:418-423`) refuses with
`1224 MinCollateralNotMet` — the code the pool-wide `min_collateral` check
also uses — when the user's collateral in that reserve, valued
`to_asset_from_b_token` (floor, `pool/src/pool/reserve.rs:230-232`), is
nonzero and below `min_position`.

It is checked on those two request types only: a fill's transfer of lot
collateral to the filler is not checked, and neither is what a partial
liquidation leaves the borrower. It binds on every live market (50 XLM and
1 USDC on XLM/USDC, for instance).

The bot's decoder looks fields up by name, so nothing fails to parse. But
`math::ReserveConfig` has no such field, and neither planner models the
rule: `plan_fill`'s primary supply can leave the filler's primary under it,
`plan_unwind`'s partial withdrawals can too, and a `min_primary_collateral`
strictly between zero and `min_position` can never be reached. The
executor answers `1224` with one re-plan at half the percent, which cannot
cure a `min_position` miss.

### 1.3 The default path's no-collateral gate (Guardian L-01)

`check_and_handle_user_bad_debt` (`pool/src/pool/bad_debt.rs:54-74`) now
values the borrower only when some collateral entry is above zero:

- liabilities and no collateral entry above zero → the default path runs,
  and no price is read;
- otherwise → it runs only if `collateral_raw == 0`, which needs prices.

`math::setoff::project_default` and `Auctioneer::decide_one` value the
borrower first in every case, so each fails with `MissingPrice` on an
unpriced reserve exactly where the contract succeeds.

## 2. Design

### A. Event topics

- `PoolEvent::DefaultedDebt` and `PoolEvent::DebtSetoff` each gain
  `user: Option<String>`.
- Three topics decode as `[name, user, asset]`, the `v0.1.1` shape. Two
  topics still decode as `[name, asset]` with no user: stock pools emit
  that `defaulted_debt`, the sandbox deploys stock wasm, and pre-release
  fork builds emit that `debt_setoff`. Any other count stays a shape error.
- `affected_accounts` returns the user when there is one, so the tracker
  re-reads that borrower in the tick that changed it. That closes the gap
  the events module doc records: a `bad_debt(user)` whose set-off clears
  the debt from the borrower's own supply used to emit no event naming
  them, leaving their row stale until the next full scan.

### B. `min_position`

1. **Decoded.** `math::ReserveConfig` gains `min_position: i128`, read when
   the entry carries it and zero when it does not (stock, and fork builds
   before Guardian L-02), so nothing changes on a pool without it.
2. **One rule, one helper.** A reserve answers whether a collateral
   position of `b` b-tokens passes: `to_asset_from_b_token(b)` — the
   contract's own floor rounding — is zero or at least `min_position`.
   Every check below goes through it.
3. **`plan_fill`.** A projection that sends a `SupplyCollateral` of the
   primary passes only if the filler's primary position after it does,
   valued against the reserves the contract holds when that request runs:
   the post-default reserves for a full fill (the fill request comes first
   and runs the borrower's default path, which can lower `b_rate`), the
   reserves as read otherwise. The b-tokens counted are the ones
   `project` already mints at the as-read rate, which a cut rate would
   only increase. Both choices value the position no higher than the
   contract will against the snapshot's state; the rate's accrual between
   the snapshot and the fill landing is covered by the top-up's allowance
   below.
   - `healthy()` requires it, so `largest_healthy_percent` and
     `first_healthy_ledger` hold it too.
   - The supply escalation raises its target to at least the top-up that
     brings the primary position to `min_position`, estimated and then
     verified by projection like every other supply. The top-up carries
     the same two-unit rounding allowance as every other supply, for the
     rate's accrual between the snapshot and the fill landing; a reserve
     whose `b_rate` a default cut to zero needs none.
   - A supply the wallet or the supply cap cannot take to the top-up is
     sent not at all — the contract would refuse it — and the percent and
     ledger searches run without one, so a later ledger whose larger lot
     carries the fill alone is still found. Only when none does is the
     skip the existing `FillSkip::Unfunded` — the wallet lacks the
     primary — or `FillSkip::SupplyCapped` when the reserve's supply cap is
     what stopped it, so no new skip reason, metric series or notification kind
     is added.
   - A plan that supplies nothing is not checked, matching the contract.
4. **`plan_unwind`.** Every partial withdrawal leaves the reserve's position
   at or above `min_position`, or takes all of it:
   - a partial's amount is capped so at least `to_b_token_up(min_position)`
     b-tokens stay, whose value is at least `min_position` by the
     conversion's rounding — for the primary, the larger of that and its own
     `min_primary_collateral` floor;
   - `take_withdrawal`, and step 2's primary withdrawal, verify the
     remaining position with the helper and refuse to plan one that fails,
     so the back-off can never send one;
   - a position already under `min_position` — reachable, since the fill's
     lot transfer is unchecked — can only be withdrawn whole.
   `WithdrawAll` leaves zero and needs no change.
5. **Startup validation.** `validate_primary_asset` refuses, in every mode,
   a pool whose `min_primary_collateral` is above zero and below the
   primary reserve's `min_position`, naming both: no unwind can ever reach
   that floor, and every attempt would be refused.
6. **Executor: unchanged.** `1224` still answers `ExecOutcome::Replan`, and
   the re-plan respects `min_position`. The re-plan reads no fresh
   snapshot, so a miss the projection could not see can recur on it; that
   costs a simulation, not a fee.

### C. The no-collateral gate

- `project_default`: when the borrower has liabilities and no collateral
  entry above zero, the gate opens without valuing anything; otherwise it
  values the borrower and requires `collateral_raw == 0`, as now.
- `Auctioneer::decide_one`: after the open-auction check and before any
  valuation, a borrower with liabilities and no collateral entry above zero
  is `Decision::BadDebt`. Everything after is unchanged.

## 3. Testing

Test-first, unit level, every case against constructed inputs:

- **Events.** Three-topic `defaulted_debt` and `debt_setoff` decode with
  their user, and `affected_accounts` names it; two-topic forms still
  decode, with no user; any other topic count is a shape error.
- **Decoder.** A `ResConfig` carrying `min_position` decodes it; the
  committed mainnet fixture, which predates the field, decodes it as zero.
- **Helper.** Zero passes; one unit under `min_position` fails; exactly
  `min_position` passes; `min_position` of zero passes everything.
- **`plan_fill`.** A partial fill whose shortfall supply would land under
  `min_position` is raised to reach it; a full fill is checked against the
  post-default reserves; a wallet short of the top-up skips `Unfunded`; a
  plan that supplies nothing is unaffected.
- **`plan_unwind`.** A partial that would leave a nonzero position under
  `min_position` is capped; a position already under it is not partially
  withdrawn; a zero `min_primary_collateral` still withdraws the primary
  whole; `min_position` of zero leaves every existing case unchanged.
- **Validation.** A floor strictly between zero and `min_position` is a
  startup error; zero, and any floor at or above it, pass.
- **L-01.** `project_default` with liabilities only, in a reserve the
  oracle cannot price, defaults without `MissingPrice`; `decide_one` answers
  `BadDebt` for such a borrower.

Every existing test must pass unchanged except where it constructs a
`ReserveConfig` literal, which gains `min_position: 0`. The sandbox still
deploys stock wasm, which carries none of these rules, so it is not run for
this change; moving it onto Precept's `v0.1.1` artefacts is the next change,
and is where these paths meet real contract code.

## 5. Out of scope

- **A pool whose reserve the oracle cannot price holds its events cursor.**
  `Tracker::refresh` values every account in its batch with `?`, so one
  holder of an unpriced reserve fails the refresh, the tracker declines the
  tick and the poller re-reads the range until the price returns. On
  Precept this is likelier than on stock: the oracle adapter answers no
  price once a feed is older than its `max_age_secs`, and a feed can be
  tripped by hand. Nothing is lost — the cursor resumes, and the contract
  refuses every priced action meanwhile — and readiness reports the lag.
  Pre-existing, separate from these three changes, and left as it is.
