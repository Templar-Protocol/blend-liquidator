# Phase 6b: Telegram, Metrics and HTTP Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Land the operational surface the spec's Phase 6 still owes: Telegram delivery behind the existing `NotificationChannel` trait with a bounded in-flight semaphore and a `drain()` on exit, every notification kind wired at its call site, dependency-free Prometheus metrics, and an axum server for `/healthz`, `/livez` and `/metrics` that runs only when a port is configured.

**Architecture:** One `Metrics` handle (atomically updated, rendered as Prometheus text) is built in `Service::run` and handed to the pollers, the tracker and auctioneer loops, the filler and the notifier; the HTTP server reads it and pings the store. `Notifier::notify` becomes fire-and-forget: the dedup entry is taken synchronously, the send runs in a spawned task behind a semaphore, and `drain()` waits for in-flight sends on every exit path. `TelegramChannel` is the second `NotificationChannel`; `LogChannel` stays the fallback and the dry-run demonstration's channel.

**Tech Stack:** Rust 2021, tokio, axum 0.8 (`default-features = false`, `http1` + `tokio`), reqwest 0.12 (already in the tree), wiremock 0.6 (dev, already in the tree), clap env args.

**Spec:** `docs/superpowers/specs/2026-09-04-blend-liquidator-bot-design.md` — §2 process shape and module map, §6 global knobs, §7 observability, §8 error handling, §10 deployment contract.

## Global Constraints

- **Secrets arrive through the environment, never as command-line arguments.** `TELEGRAM_BOT_TOKEN` is read by `main.rs` from the environment like the signing keys, never a clap field; it renders as `Secret(<redacted>)` and never reaches a log line, an error `Display`, a URL that is logged, or a notification's text.
- **`DRY_RUN` defaults to `true`**; nothing in this phase touches the parser or the submission gates. A dry run still sends no transaction.
- **Notifier and metrics failures never affect trading** (spec §8): `Notifier::notify` returns no `Result`; a metrics call never fails; an HTTP bind failure is logged and the bot keeps trading.
- Spec §6 defaults, verbatim: `PORT` / `HTTP_PORT` u16 unset (unset disables the server; `PORT` honoured for Cloud Run), `HTTP_BIND_ADDR` IP `127.0.0.1`, `TELEGRAM_BOT_TOKEN` / `TELEGRAM_CHAT_ID` unset — both or neither, `HEALTH_MAX_LAG_LEDGERS` u32 `10`, `FAILURE_NOTIFICATION_COOLDOWN_HOURS` u64 `24` (exists).
- Spec §7: metrics are Prometheus text at `/metrics`, prefixed `blend_liquidator_`; label sets are closed enums. `/healthz` is readiness: 200 when the processed ledger is within `HEALTH_MAX_LAG_LEDGERS` of chain head and the store answers a ping, else 503 with the reason. `/livez` is liveness: 200 while the poller loop has recorded a heartbeat within five poll intervals regardless of whether the RPC is answering, else 503. *Corrected during review:* both probes ended up stricter than this line. `/healthz` also fails when no chain head has been read for a pool within the liveness deadline — both ledger gauges are this process's own, so an RPC outage freezes the lag wherever it was and a readiness that compared only the two would answer 200 through the very failure it exists to catch. `/livez` measures against `PollerConfig::liveness_deadline` (`LIVENESS_INTERVALS × poll_interval + max_backoff`, 35 s at the defaults) rather than five bare intervals, because the backoff after a failed pass is a stretch of the loop that stamps nothing; a pool that has never heartbeated is measured from `HttpState::started` instead, so a first start against a busy pool is not read as a poller that has stopped. The body is still the first failure, and `/livez` is still the restart probe.
- Spec §10: `PORT` is honoured when set; a restart probe must target `/livez`, never `/healthz`; the Docker `HEALTHCHECK` stays `pgrep` (it is a liveness check, and the Dockerfile's own comment says why it must not become `/healthz`). Exit codes stay `0`/`1`/`2`/`130`; the `130` path (second signal) exits without draining, deliberately.
- `clippy::pedantic` with `unwrap_used = "deny"` (tests exempt via `clippy.toml`); structured `tracing` only; doc comments state constraints and invariants; money is never `f64` except for display — the one place this phase shows a money value as a float is the `estimated_profit_total` metric, which is display. *Corrected during review:* it shows none. The metric renders the raw `i128` total in the pool oracle's own units: the oracle's decimals are the pool's to read, not this bot's to assume, so there was no scale to divide by. No `f64` appears in this phase at all.
- `make check` green at the end of every task; a scripted test asserts what it scripted was consumed (`rpc.remaining() == 0`, `wiremock` expectations verified).
- Test count = `#[test]` + `#[tokio::test]` + `#[sqlx::test]`; 476 at this plan's base (`9e2f201`).

## Facts the code is written against

### Telegram Bot API

`POST https://api.telegram.org/bot<TOKEN>/sendMessage` with JSON `{"chat_id": "<id>", "text": "<text>", "disable_web_page_preview": true}` answers `200 {"ok": true, "result": {...}}` or a non-2xx `{"ok": false, "description": "..."}`. `GET https://api.telegram.org/bot<TOKEN>/getMe` answers `{"ok": true, "result": {"username": "..."}}` and is how a token is verified. `text` is at most 4096 characters. **The token is part of the URL**, so a `reqwest::Error`'s `Display` can carry it: every `reqwest::Error` is passed through `Error::without_url()` before it is formatted anywhere.

## Rulings taken before execution

1. **Metrics are a passed handle, never a global.** `Arc<Metrics>` is built once in `Service::run` and threaded to every site; a test builds its own and asserts on it. One `std::sync::Mutex` around the whole state, held for a few instructions and never across an `.await` (the notifier's `lock` shape, poison recovered).
2. **`Notifier::notify` is fire-and-forget.** It takes the dedup entry synchronously, tries a permit from a semaphore of `NOTIFY_IN_FLIGHT = 10`, and spawns the send. It answers `Delivery::Queued`, `Delivery::Deduplicated`, or `Delivery::Dropped` (no permit: the entry is rolled back and the notification is logged through `LogChannel` so it is not lost). A send that fails inside the task rolls the entry back and logs through `LogChannel` too. `Delivery::Sent`/`Failed` go away: nothing can know synchronously whether Telegram accepted a message, and trading never waits for it. The filler's `leftovers_notified` rollback moves from `Failed` to `Dropped`.
3. **`drain()`** acquires every permit with a `DRAIN_BUDGET = 10 s` timeout and is called at the end of `Service::run` on both the `Ok` and the `Err` path, after `drain_tasks`. The second-signal `exit(130)` path does not drain, deliberately (spec §10's escape hatch).
4. **`LogChannel` is the fallback, not a second channel:** with Telegram configured the notifier's channel is Telegram alone; `LogChannel` is what a dropped or failed delivery falls back to, and what an unconfigured deployment gets.
5. **The liveness window includes the poller's backoff.** The poller records a heartbeat at the top of every loop iteration; during an RPC outage it sleeps up to `max_backoff` (30 s) between iterations, so "five poll intervals" alone would fail `/livez` during exactly the outage spec §7 says must not fail it. `PollerConfig::liveness_deadline()` is `5 × poll_interval + max_backoff`; `/livez` and the watchdog both use it.
6. **`PollerStalled` comes from a watchdog task**, not from the poller (a wedged loop cannot report itself): once per `poll_interval` it compares every pool's heartbeat against the liveness deadline and notifies `PollerStalled` (High) for each pool past it; the cooldown deduplicates repeats. No recovery kind exists in spec §7, so recovery is an `info` log.
7. **`RpcFailing`** is the poller's: after `RPC_FAILING_AFTER = 5` consecutive `poll_once` failures (the backoff is then 16 s) it notifies once (High); a success resets the count and logs recovery.
8. **`AuctionCreated` (Low) and `BadDebtReported` (Medium)** are sent for a creation whose submission `Succeeded` on chain — nothing else is "created". A dry run therefore never sends them; its creations are logged as before.
9. **`FillConfirmed` (Low)** on a fill's `Succeeded`; **`FillFailed` (High)** on `Failed` (it consumed a sequence number and a fee); `Expired` and `Unknown` are logged, not notified.
10. **`SubmissionDropped` (High)** is sent by the caller that owns the outcome — the filler on `ExecutorError::Queue(QueueError::Chain(_))`, the auctioneer loop on `AuctioneerError::Queue(QueueError::Chain(_))` — because `QueueError::Chain` is answered only after the retry budget for a failure that sent nothing. The unwind's setback alert keeps using it.
11. **`UnfundedFill` (Medium)** on `FillSkip::Unfunded`; **`EventGap` (High)** in the tracker loop's `Gap` arm.
12. **Metric sites and label sets:** `skips_total{reason}` maps `FillSkip::{Unprofitable, PastAuctionEnd}` → `unprofitable`, `{TooManyPositions, Health}` → `health`, `Unfunded` → `unfunded`; a row `PoolConfig::supports` rejects → `unsupported_assets`; a refusal (`ExecOutcome::Refused`, the second refusal after a re-plan) → `contract_error`. `creations_total{result}` and `fills_total{result}` count `attempted` on every `Recorded`, `succeeded` on `Succeeded`, `failed` on `Failed` or `Expired`. `estimated_profit_total` adds `est_profit` (oracle units) on a `Succeeded` fill and renders `/ 1e7` as a float — display only. *Corrected during review:* it renders the raw integer, unscaled — see the Global Constraints note — and gained a sibling `estimated_loss_total`, because a `force_fill` pool can land a fill whose estimate is negative and a Prometheus counter that decreases is read as a reset. A skip is also counted once per auction *per reason* (`FillerState::counted_skips`), not once per planning attempt: the filler re-makes each of these decisions every tick, so an auction it refuses forever would otherwise bury the other four reasons. `reserved_inventory{asset}` is `Inventory::reserved()` after every filler tick. `users_tracked{pool}` is set wherever `count_users` is already read (the seed and the full scan). Pool and asset labels are bounded by the configuration; everything else is an enum.
13. **`/healthz`** needs every configured pool: `head` and `processed` both known and `head − processed ≤ HEALTH_MAX_LAG_LEDGERS`, then `Store::ping`. Before the first tick it is 503 `no ledger processed yet for <pool>`. The reason is the response body, plain text.
14. **HTTP is optional and never load-bearing:** no port → no task; a bind failure → `error!` and the task returns `Ok(())`. `PORT` wins over `HTTP_PORT` when both are set.
15. **`check-config` verifies Telegram** with `getMe` when configured and reports the bot's username; a failure is a configuration error (exit 2), because spec §10 makes `check-config` the deploy smoke test.
16. **Telegram is one crate module, `src/notifier/telegram.rs`,** under `notifier.rs` (`pub mod telegram;` in a non-`mod.rs` parent is ordinary 2018-edition layout); `metrics.rs` and `http.rs` are top level as the spec's map names them.
